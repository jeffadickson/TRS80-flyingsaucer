Assembly Demystified · Flying Saucers (Radio Shack, 1979)

Half the Time, Waiting

Could it have run faster? What was possible in 1979, measured.

What Arnstein got rightUnder the constraints

Flying Saucers had to fit a 4K Model I, load from a cassette, run under Level I or Level II, and play smoothly. It does all of that. The whole game, its pictures and its text fit in {{fig:game_bytes}} bytes with the stack in the last {{fig:stack_bytes}}. Shots and fragments share one movement routine. Collisions cost a read of video memory. And its pace is counted in passes, each padded by the same fixed delay, so it plays at the same speed on every stock Model I. The one place it visibly stops is on purpose: each hit holds the game still for the explosion ({{fig:d5.boom_ms|.0f}} ms), and the super saucer's three flashes hold it for {{fig:update_max_ms|.0f}} ms.

More than half of every pass is the wait. Of the rest, the two biggest costs do almost nothing a player sees. RANDOM runs its 23-step shift register on every pass to give a new saucer a 1-in-256 chance. SHOW_COUNTS prints all ten digits of the score, hits and shots on every pass, whether they changed or not.

P1 · The same random numbers, soonerPeriod-feasible

RANDOM shifts its 16 bits through the accumulator: LD A,H / RRA / LD H,A, then the same for L. The Z80 can rotate the registers themselves, and DJNZ counts down in one instruction. The rewritten loop gives exactly the same numbers: I ran {{opt:port_cases}} random seeds through both on the emulator and {{opt:port_identical}} matched in every register and in the stored seed. It saves {{opt:random_saving_t}} T-states a call and four bytes.

The saving is small, because what makes RANDOM slow is the 23 steps, and fewer steps would give different numbers. A different generator, or reading the Z80's refresh register with LD A,R to decide on a new saucer, would be far cheaper, but it would also make a different game, so I have not built it.

P2 · Print the counts only when they changePeriod-feasible

The score, hits and shots change only when something is hit, escapes or is fired. P2 keeps the last low byte of each in three bytes that the original never uses, compares, and calls SHOW_COUNTS only when one differs or the screen has just been cleared. Every change to one of the counts changes at least one of those three bytes, so nothing is ever left unprinted. The room comes from the code the original can never run: the always-false top-row test in front of the dead −20 branch, and the branch itself (see Secrets in the Code).

Visible effect: none, unless it is spent. The game's speeds are counted in passes, so a shorter pass would simply make the whole game run that much faster; to play as before, DELAY would wait that much longer. The saving is headroom: room for more saucers on the screen, or for drawing them in finer steps, without the game slowing down. The game was not short of time. It was short of memory, and both changes fit in the original's own bytes only because it had unreachable code to give up.
