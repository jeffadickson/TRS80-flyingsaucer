Assembly Demystified · Flying Saucers (Radio Shack, 1979)

Hidden in the Code

Secrets in the code: the bugs, the leftovers, and a penalty no one ever paid.

Every instruction of the program was traced on the emulator through eight scenarios, {{calc:passes_total}} passes of the game loop in all. Everything ran except three short pieces of code, and each of those turns out to be impossible to reach. Those three, and the other things the listing gives away, are below.

The penalty no one paidDead code at 4A7Eh

When a shot moves into an empty cell, the program first checks whether that cell is in the top row, and if it is, removes the shot and takes 20 points off the score. That check can never succeed. A few instructions earlier, at 485Dh, every shot that reaches the top row is already removed, for 2 points. So 35 bytes at 4A7Eh, the −20 and its bookkeeping, have never run. My guess is that the −2 check was added later and the old one left in; the code cannot tell us which came first.

{{code:4A72:4A84:The test that is never true, and the start of the branch behind it. The manual and the screen both say a missed shot costs 2.}}

An escape that costs nothingA bug at 4712h

A saucer that flies off the screen costs a point, unless the score is already 0. The test for 0 looks only at the low byte of the score, LD A,L / OR L, so at 0100, 0200 and every other whole hundred the program decides the score is 0 and takes nothing off. On the emulator, with the score set to 0100, {{fig:escape_from_0100.escapes}} saucers escaped and the score stayed {{fig:escape_from_0100.score_after}}. Because of it, the code that would borrow from the hundreds digit (471Fh) can never run either.

{{code:470F:4723:The escape penalty. OR L tests L twice; OR H was presumably meant.}}

And the unreachable code behind it has a bug of its own: at 471Fh it adds 99h to the high byte with no DAA after it, so, had it ever run, the score's hundreds and thousands would not have been a decimal number.

The keys the screen gets wrong2Ch and 2Eh

The title screen says to aim with < and >; the manual says the arrow keys. The program turns the cannon only for the codes of , and . without SHIFT. SHIFT with those keys (the < and > printed on them), and both arrow keys, all fire a shot instead, as the emulator shows. A player who followed the screen literally fired every time they tried to aim.

Hits that don't countMeasured

A saucer is found by its lights row only. A shot that explodes in a saucer's dome scores nothing and the saucer flies on. In the robot's game at difficulty 5, {{fig:explosions.dome_row}} of {{fig:explosions.total}} shot and fragment hits were like that. The Screen Is the World explains why.

A table that ends by luck4CD8h, an inference

The saucer table ends with an FFh that the program writes when the game starts. The shot table ends with an FFh too, at 4CD8h, but nothing in the program ever writes it: it is in the tape. Around it, the tables on the tape hold a repeating FFh, 00h pattern, the look of memory that was never initialized, saved along with the program. 4CD8h falls on an FFh of that pattern. I think the end mark is there by luck, saved from the author's machine; had that byte been 00h, the shot loop would run on past its table into the text that follows. That is an inference: the bytes cannot tell us whether it was put there on purpose.

The routine that finds a record for a newly fired shot (4B3Ch) does not look for the end mark at all: it takes the first free record, wherever it is. With all 20 records busy, the next shot would be written over the HITS and SHOTS labels after the table. It never comes close. Firing as fast as the keys allow, at difficulty 1, for {{fig:shot_table.fields}} fields, the busiest moment used {{fig:shot_table.highest_used}} of the {{fig:shot_table.records}} records.

LeftoversWritten, never read

  • HIT_ADJUST (4D01h) is set to 0 before every target search and added to the hit cell after a hit. It is never anything but 0.
  • BOOM_COUNT is set to 3 and counted down while a hit's explosion is drawn, but nothing there tests it; only the super saucer's flash uses it as a counter.
  • NEW_RIGHT is stored for every saucer that starts on the right and never read. A leftward saucer's second address (bytes 3 and 4 of its record) is increased every step it moves left, and never read either.
  • Eighteen bytes are never touched at all: SPARE (4 bytes), SPARE2 (2), SPARE3 (2), SPARE4 (3), and a second string of six blanks and its end mark at 4E2Dh (7) that nothing prints.

The demonstration plays by different rulesSelf-modifying code at 4514h

Pressing D rewrites one byte of the program: the mask on the 1-in-256 roll for a new saucer becomes 7Fh, so in the demonstration saucers appear twice as often. The demonstration presses its own keys from a four-byte table, Z . , Z, about four passes in 256. It starts at difficulty 4 (the D key's code, 44h, gives 4) and, after its GAME OVER, starts again by itself at difficulty 1, because the pause routine it has just used leaves a 1 behind.

TIME isn't secondsMeasured

The TIME counter starts at 90 and counts down one unit every PACE+204 passes. Measured on the emulator, a unit lasts {{fig:d9.time_unit_s|.2f}} s at difficulty 9 and {{fig:d1.time_unit_s|.2f}} s at difficulty 1: the 90 on the screen lasts {{calc:t90_d9}} seconds at difficulty 9 and {{calc:t90_d1}} at difficulty 1, so the "hard" game is the longest.
